# AEAD Audit — 2026-04-10

**Scope:** Every `ciphertext()` column in the Drizzle schema.
**Methodology:** For each column, document the encrypt call site, decrypt call site, label, AAD construction, and status (PASS / FIX / INFO). FIX rows are tracked for resolution in subsequent Tier 0 tasks per the per-schema breakdown in `docs/superpowers/plans/2026-04-10-security-tier-0-albrecht-hardening.md`.

#### Notes on columns outside the `ciphertext()` type but in the same schema

The plan template originally listed `records.call_records.encrypted_content` with `LABEL_NOTE_KEY`. In the current schema that field is declared as `text('encrypted_content')` on both `call_records` and `note_envelopes`, **not** as a `ciphertext()` column. The note content is encrypted entirely client-side (E2EE, per-note forward secrecy; see `encryptNote` / `decryptNote` in `src/client/lib/crypto-worker-helpers.ts` and `src/client/lib/queries/notes.ts`). The server only stores the opaque ciphertext blob and never performs an AEAD operation on it, so it is not in scope for this audit. It is documented here only to record that the template entry has been intentionally removed after reality-checking the schema.

#### Per-service write-path inventory for contacts / conversations / signal_contacts

- `contacts.ts#createContact` — **passthrough**. Accepts client-produced `encryptedDisplayName`, `encryptedNotes`, `encryptedFullName`, `encryptedPhone`, `encryptedPII` ciphertexts and their recipient envelopes; writes them verbatim. The actual AEAD operation is client-side (`create-contact-dialog.tsx` inline `envelopeEncrypt`). Server holds no opportunity to insert AAD — the Tier 1 primitive rewrite must simultaneously update both the client write helpers and the server passthrough contract (so the API body carries the bound AAD context or reconstructs it from the `contactId` that the server assigns).
- `contacts.ts#updateContact` — **passthrough**, same as create. A subtlety for the Tier 1 plan: the `contactId` is assigned server-side on create, so the client CANNOT compute the final record-bound AAD before the first POST. Tier 1 will need to resolve this (e.g. client generates the UUID, or server re-wraps the ciphertext with the assigned id).
- `contacts.ts#createRelationship` — **passthrough** for `encryptedPayload`. Same server-assigns-id concern as above.
- `conversations.ts#createConversation` — **server-side envelope**. Uses `this.crypto.envelopeEncrypt(data.contactLast4, recipientPubkeys, LABEL_USER_PII)`. This is the only server-side AEAD write in this audit section and is the only row that could be fixed in Tier 0 without touching client code — but the primitive `CryptoService.envelopeEncrypt` does not accept an AAD parameter today, which is exactly the reason Tier 1's primitive rewrite is a hard dependency. No current caller passes `contactLast4`, so even the data risk is dormant until a messaging provider starts plumbing it in. FIX deferred.
- `signal-contacts.ts#upsert` — **passthrough** for `identifierCiphertext`. Client (`signal-contact-registration.ts`) is the only encrypt site, and unlike the contacts inline helper it already uses the AAD-parameterized `cryptoWorker.envelopeEncryptField` path — so a Tier 0 one-line fix (`utf8ToBytes(`${LABEL_SIGNAL_CONTACT}:${userPubkey}:identifier_ciphertext`)`) would be possible if there were already a decrypt path. There is not, so deferring to Tier 1 does not regress anything.

#### Notes on findings

- **No unencrypted writes discovered.** Every `ciphertext()` column audited is written with a real envelope or `ciphertext()` payload; there is no path where a plaintext string or empty string would slip into one of these columns.
- **No orphaned schemas.** Every column has at least one identifiable write path; `encryptedPII` is the only column in the contacts schema with no production UI populating it today, but the plumbing through `CreateContactInput` and the discovery/import routes is intentional and already tested — it is a reserved slot, not dead code. `conversations.encrypted_contact_last4` is similarly reserved but wired end-to-end on the server side.
- **Label reuse concerns surfaced for Tier 1.** Two columns share a label with unrelated tables:
  - `conversations.encrypted_contact_last4` shares `LABEL_USER_PII` with `users.encrypted_name`, `users.encrypted_phone`, `bans.encrypted_phone`, `bans.encrypted_reason`, and `call_records.encrypted_caller_last4`. This is the widest reuse in the audit so far. Tier 1's new-label matrix should split these per table at minimum, or enforce column binding via AAD.
  - `contacts.encrypted_full_name` / `encrypted_phone` / `encrypted_pii` all share `LABEL_CONTACT_PII`. This reuse is narrower (one table, one record) but the cross-field swap problem still applies — Tier 1 should bind `column_name` into the AAD for these.
- **Client inline `envelopeEncrypt` duplication.** `create-contact-dialog.tsx` defines its own `envelopeEncrypt` function (lines 41–54) rather than going through `cryptoWorker.envelopeEncryptField`. Tier 1's primitive rewrite should consolidate this duplicated helper into the worker RPC so there is exactly one encrypt path on the client, making AAD binding a single edit.

- `subscribers.encrypted_identifier` is `text(...)`, not `ciphertext()`. Per the comment in the schema it is an XChaCha20-Poly1305 payload encrypted with the hub key as raw `hex(nonce(24) || ciphertext)` — the historical pre-`ciphertext()`-column format. The server writes it at `subscribers.ts#createSubscriber` verbatim (passthrough) and never decrypts it. Tier 1's primitive rewrite should either migrate this column to the `ciphertext()` type (so it gains the same AAD treatment as the hub-field tier) or convert it to the hub-field tier directly. Flagged in follow-up notes below.

#### Notes on findings

- **All written columns are PASS.** The five written columns in this section (`blasts.encrypted_name`, `tags.encrypted_label`, `tags.encrypted_category`, `report_types.encrypted_name`, `report_types.encrypted_description`) all go through the client-side hub-field tier, which binds AAD to `${LABEL_HUB_FIELD}:${recordId}:${fieldName}` on both encrypt and decrypt. Replay protection across rows, columns, and tables is in place.
- **Three orphan columns.** `blast_settings.encrypted_double_opt_in_message` / `encrypted_welcome_message` / `encrypted_bye_message` are defined in the schema but have no write site and no decrypt site in the codebase. The `/api/blasts/settings` route does NOT operate on this table; it reads/writes `settings.messagingConfig`. These are reserved slots. Recommend either wiring them up with the hub-field tier when the double-opt-in / welcome / bye feature ships, or dropping them in a schema cleanup. No Tier 0 or Tier 1 action needed because there is no ciphertext in existence that could be swapped or replayed.
- **`subscribers.encrypted_identifier` format drift.** Declared as `text(...)` with a raw `hex(nonce || ciphertext)` encoding that predates the `ciphertext()` column helper. Server passes it through verbatim; never decrypts. Tier 1's primitive rewrite should bring this onto the hub-field tier (or equivalent AAD-bound path) so replay protection is uniform across the hub-key org-metadata family. Tracked as a Tier 1 follow-up.
- **`CreateBlastData.encryptedName` fallback is plaintext.** As with other hub-field columns, the server falls back to writing the plaintext `name` when the client has no hub key (e.g. immediately after PIN unlock with an uninitialized hub-key cache). This is already flagged in the general "plaintext server-fallback" pattern and is not specific to this audit section — `decryptHubField` handles both the AAD-bound ciphertext case and the plaintext-passthrough case on read.

#### Notes on findings

- **Hub-field tier: 2 PASS, 5 FIX-for-fallback, 0 label-only on the client path.** The client-driven write paths through `encryptHubField` all PASS (hubs 2 cols, roles 2 cols, plus tags/report_types/blasts/teams/shifts/firehose in other sections). The server-side fallback/seeding paths in `role-management.ts#listRoles` and `custom-fields.ts#updateCustomFields` still produce label-only ciphertext because `cryptoService.hubEncrypt` has no AAD parameter — these are the only hub-field tier ciphertexts in the whole codebase with broken AAD.
- **`custom-fields-section.tsx` is the odd one out.** Unlike every other hub-field admin section, it does not call `encryptHubField` on the client; it relies entirely on the server-side fallback. Tier 1 should move the encrypt call to the client to match the pattern used by hubs, roles, tags, teams, shifts, report_types, and blasts. This is flagged as a Tier 1 follow-up in the new-label / encrypt-site migration matrix.
- **`LABEL_PROVIDER_CREDENTIAL_WRAP` is the widest label reuse family in the whole audit so far.** It is reused across:
  - `geocoding_config.encrypted_api_key`
  - `provider_config.encrypted_brand_sid`, `encrypted_campaign_sid`, `encrypted_messaging_service_sid`, `encrypted_credentials`
  - `signal_registration_pending.encrypted_number`
  - `telephony_config.config` (text column, out of strict scope)
  - `messaging_config.config` (text column, out of strict scope)
  This is 7 columns (or 5 `ciphertext()` columns strictly in scope) sharing a single label — AEAD replay is possible across all of them. Tier 1's new-label matrix must split this family per column at minimum and bind the singleton row identifier for the single-row tables (`geocoding_config`, `provider_config`, `signal_registration_pending`, `telephony_config`, `messaging_config`).
- **`LABEL_IVR_AUDIO` is single-use** but the `ivr_audio` composite primary key `(hubId, promptType, language)` must be bound into AAD. Without it, an attacker could swap prompt audio across hubs/prompts/languages at will, and the server would serve the swapped audio to callers. This is a high-impact FIX because the audio is directly reachable by callers dialing the hotline.
- **Two orphan columns.** `report_categories.encrypted_categories` (stub service function, no route caller, no UI producer) and the three `blast_settings` columns from the previous section. Neither has a write path that produces ciphertext today, so there's nothing to FIX — they are tracked as schema cleanup follow-ups.
- **Client-side plaintext fallback is the saving grace for the hub-field FIX rows.** In dev/test environments without a populated hub-key envelope list, the server-side `hubEncrypt` path simply returns plaintext via the `encryptOrPassthrough` helper (`custom-fields.ts` line 70) or the ternary on `role-management.ts` line 59. The client's `decryptHubField` handles plaintext input by returning it as-is, so the UI is not broken today. The FIX is only triggered in production environments where the server is in the hub-key envelope list (e.g. a super-admin server deployment); until then the bug is latent.

#### Notes on findings

- **3 PASS, 2 FIX, 1 INFO.** The hub-field tier columns (teams 2, shifts 1) all PASS through the client-side `encryptHubField` path. The calls columns (`active_calls.encrypted_caller_number`, `call_legs.encrypted_phone`) are the FIX rows — both use `LABEL_EPHEMERAL_CALL` with label-only AAD. `ring_groups.encrypted_name` is INFO (orphan — no live ciphertext).
- **`LABEL_EPHEMERAL_CALL` shared between two tables.** The two calls columns form a shared-label family of 2: an attacker with DB write access could swap ciphertexts between the two tables and the server would accept either as the other. Impact is limited by the fact that the decrypted value is immediately consumed by the telephony adapter (which will likely fail or route to the wrong number), but the AEAD layer should reject this rather than rely on downstream semantic validation. Tier 1's new-label matrix should either split `LABEL_EPHEMERAL_CALL` into `LABEL_ACTIVE_CALL_CALLER` + `LABEL_CALL_LEG_PHONE` or bind the row identifier (`callSid` / `legSid`) into AAD.
- **No client-side decrypt for calls.** The `active_calls` and `call_legs` data is consumed exclusively server-side (routing decisions, admin active-calls view is populated by the server after server-side decrypt). This means the FIX can be applied entirely in `calls.ts` + `crypto-service.ts` without touching client code — but because `cryptoService.serverEncrypt`/`serverDecrypt` have no AAD parameter today, the primitive rewrite is still a prerequisite. Tier 1 remains the right home for this work.
- **Ephemeral lifetime makes the risk narrower but not zero.** `active_calls` and `call_legs` rows are deleted when the call ends; an attacker's window to swap ciphertexts is the duration of the live call. However, the impact of a swap during a live call is high — wrong number routing can directly expose a volunteer's phone to an attacker or route a caller to an unintended destination. Tier 1 should prioritize this FIX even though the lifetime is short.
- **`ring_groups` orphan is consistent with `blast_settings` and `report_categories` orphans from the previous section.** There is a small cluster of "reserved for future feature" encrypted columns in the schema. Tier 1's cleanup pass should either wire them through the hub-field tier (once their UI lands) or drop them to keep the AEAD audit surface minimal.

#### Notes on findings

- **1 PASS, 10 FIX, 1 INFO.** The one PASS is `firehose_connections.encrypted_display_name` (hub-field tier). The ten FIX rows span three label families: `LABEL_USER_PII` (5 in this section, 9 total across the audit), `LABEL_PUSH_CREDENTIAL` (3), and singleton labels `LABEL_SESSION_META` (1) and an eleventh on the push device label. The one INFO is `contact_intakes.encrypted_payload` (unexercised).
- **`LABEL_USER_PII` is now the widest label reuse in the audit** — 9+ columns across 5 tables. Tier 1's new-label matrix must split this per table AND per column at minimum, because the envelopes within the family share ECIES reader sets (the user + admins) and the AEAD layer will accept cross-column swaps between:
  - `users.encrypted_name` ↔ `users.encrypted_phone`
  - `users.encrypted_name` ↔ `webauthn_credentials.encrypted_label` (for the same user)
  - `users.encrypted_phone` ↔ `bans.encrypted_phone` (super-admin is the reader on both)
  - `users.encrypted_phone` ↔ `call_records.encrypted_caller_last4` (same super-admin readers)
  - `users.encrypted_phone` ↔ `conversations.encrypted_contact_last4` (dormant but wired)
  - `users.encrypted_phone` ↔ `invite_codes.encrypted_phone` (same super-admin readers)
  - `invite_codes.encrypted_name` ↔ `invite_codes.encrypted_phone`
  - `push_subscriptions.encrypted_device_label` ↔ all of the above
  This is the most significant cross-table replay surface in the whole codebase and the primary reason Tier 1's primitive rewrite is a hard prerequisite for Tier 0 completion.
- **`LABEL_PUSH_CREDENTIAL` family** is limited to one table (`push_subscriptions`, 3 columns) but the cross-column swap inside a single row would cause real operational breakage (web push send would use the wrong field as the wrong input to the push algorithm). The server would detect the failure downstream, but the AEAD layer should reject it first. Tier 1 should bind the row id into AAD.
- **`LABEL_SESSION_META`** is single-use but still needs per-session binding. The swap risk is narrow (an attacker can only swap two sessions of the same user) but real — the admin session list would display incorrect IP / UA / geolocation for a given `sessionId`, which could mask a real account takeover event. Tier 1 should bind `sessionId` into the session-meta AAD.
- **`contact_intakes.encrypted_payload` is the fifth orphan column discovered in this audit** (alongside `blast_settings.*`, `report_categories.encrypted_categories`, `ring_groups.encrypted_name`). The pattern of "schema + server service + route + client query hook — but no UI caller" is consistent across these orphans. Tier 1 cleanup should either wire each one through or remove it.
- **Server-key fallback is the dominant encrypt pattern for PII.** `users.encrypted_name`/`users.encrypted_phone` and `invite_codes.encrypted_name`/`encrypted_phone` all have a server-key fallback path for cases where envelope encryption isn't possible (e.g. no admin pubkeys configured). These fallback ciphertexts share the same `LABEL_USER_PII` with the envelope ciphertexts, so cross-row swaps are possible between a fallback-encrypted row and an envelope-encrypted row. Tier 1 should consider whether the fallback needs its own label or whether the fallback path should be removed entirely (envelope-or-nothing).
- **Client-side decrypt for envelope-encrypted PII still hard-codes `aad = utf8ToBytes(label)`** at `src/client/lib/decrypt-fields.ts` line 153 (`decryptFieldWithRecovery`). This is the single line on the client that needs to change when Tier 1 introduces per-record AAD for envelope columns. Every FIX row in this section and every envelope-style FIX in earlier sections (bans, contacts, conversations, signal_contacts, sessions, users, invites, webauthn, push device label) flows through this function.

Unlike the schema-by-schema audit above, "export paths" may not always terminate in a `ciphertext()` column — some write to blob storage, some return a JSON bundle, and some pass through client-supplied envelopes without the server performing any AEAD operation.

Source files audited:

### Voicemail (RustFS via StorageManager)

- **Encrypt call site:** `src/server/lib/voicemail-storage.ts#storeVoicemailAudio` line 60 → `crypto.envelopeEncryptBinary(audioBytes, adminPubkeys, LABEL_VOICEMAIL_WRAP)`. The resulting ciphertext is hex-decoded and written to object storage via `FilesService#putAssembled` under a generated `fileId`; the per-recipient ECIES envelopes are persisted as `FileKeyEnvelope[]` on the `files` record.
- **Decrypt call site:** client-side attachment flow via `FilesService` + `src/client/lib/file-crypto.ts#decryptFileForRecipient`. The voicemail is surfaced through the standard encrypted-file read path — the voicemail row in `call_records.voicemailFileId` points at a `files` record, which the client fetches, decrypts with their ECIES envelope, and plays back.
- **Label:** `LABEL_VOICEMAIL_WRAP` (`llamenos:voicemail-audio`, index 12 in `LABEL_REGISTRY`). Transcript path `LABEL_VOICEMAIL_TRANSCRIPT` is defined but has **no active encrypt site** in the current branch — voicemail transcripts are dormant/unwired.
- **AAD (actual):** `utf8ToBytes(LABEL_VOICEMAIL_WRAP)` — label only, **not** bound to the `voicemailFileId`, the `callSid`, or the `hubId`. The AAD is synthesized inside `CryptoService#envelopeEncryptBinary` at `src/server/lib/crypto-service.ts` line 175 and is not parameterizable at the call site.
- **Framing metadata covered:** none of `fileId`, `contextId` (= `callSid`), `hubId`, or the content-type/MIME are part of the AEAD AAD. They are recorded in plaintext on the `files` DB row (`context_type`, `context_id`, `hub_id`), which means: (a) an attacker with DB write access can repoint a `call_records.voicemail_file_id` at a different `files` row of the same reader set (another voicemail for the same admins), and the AEAD layer will not reject the swap; (b) a `files` row's `context_type`/`context_id` can be rewritten to associate an unrelated encrypted blob with a different call.
- **Status:** **FIX — Deferred to Tier 1 — primitive rewrite.** The voicemail encrypt path flows through `CryptoService#envelopeEncryptBinary`, which hard-codes `aad = utf8ToBytes(label)` at line 175 and does not accept an AAD parameter. The matching decrypt path on the client (`file-crypto.ts#decryptFileForRecipient`) already takes a per-file AAD because it was rewritten in Workstream 0.1 Task 8, but the server-side binary envelope wrapper has NOT been rewritten yet. Fixing this in Tier 0 would require either (1) plumbing an AAD argument through `envelopeEncryptBinary` (touches the crypto service interface; parallel work with Tier 1's HPKE rewrite that replaces the whole primitive) or (2) dropping the wrapper and inlining a direct `symmetricEncrypt` + `eciesWrapKey` call in `storeVoicemailAudio`, which would duplicate the wrapper's logic and diverge from the rest of the envelope call sites. Neither is in scope for Tier 0; Tier 1 replaces `envelopeEncryptBinary` wholesale with an HPKE-based seal that takes AAD on every call (see `docs/superpowers/plans/2026-04-10-security-tier-1-hpke-primitives.md`). Target AAD post-Tier 1: `${LABEL_VOICEMAIL_WRAP}:${fileId}:${hubId}` (and for the dormant transcript path: `${LABEL_VOICEMAIL_TRANSCRIPT}:${fileId}`).

## 2026-04-11 post-impl deep review findings

Post-implementation review of PR #68 (Tier 0 impl) surfaced additional AEAD-adjacent findings that were resolved on the branch. Documented here so future audits have a continuous record.

### Worker-boundary AAD propagation (Tier 1 must-fix)

**Where:** `src/client/lib/crypto-worker-client.ts`, `src/client/lib/crypto-worker.ts`.

The crypto worker RPC (`cryptoWorker.decrypt` / `cryptoWorker.encrypt`) does not forward a caller-supplied AAD into the inner XChaCha20-Poly1305. ECIES unwrapping uses label-based domain separation (brand + HKDF + wire-format label), but the inner AEAD is called with empty AAD. Any caller that tries to "bind" an AAD by passing one to the RPC today is silently ignored.

In Tier 0, the `file-crypto.ts` call sites were updated to **not pass** a zero-length `Uint8Array` (which was misleading about the binding), with inline comments explaining the temporary gap. The RPC signature intentionally omits the AAD parameter to keep the gap visible rather than to simulate binding.

**Tier 1 fix:** Add `aad: Uint8Array` to the worker RPC, marshal as hex, thread into the inner AEAD. Add a worker-level AAD-mismatch test that builds a ciphertext with AAD A inside the worker and asserts decrypt fails under AAD B. Update every call site in `file-crypto.ts`, `hub-field-crypto.ts`, and `decrypt-fields.ts`.

### `decryptEnvelopeField` AAD coverage audit (Tier 1 must-fix)

**Where:** `src/client/lib/decrypt-fields.ts`, `src/client/lib/crypto-worker.ts`.

The worker-side `decryptEnvelopeField` helper already takes an `aad` parameter (it was added in the envelope-v2 work). Audit every call site to confirm the AAD passed at decrypt actually matches the AAD used at encrypt. Known incomplete areas:

- `decryptObjectFields` / `decryptArrayFields` currently use label-only AAD, not record-id-bound AAD. Envelope-per-recipient provides some indirect binding (the wrapped key is bound to the recipient's pubkey) but a ciphertext can still be transplanted between records at the same label. Tier 1 should bind AAD to the record id at the source call sites.
- `file-crypto.ts decryptFileMetadata` — verify `encryptMetadataForPubkey` constructs the identical AAD byte-for-byte.

### Hub-field AEAD binding — Tier 0 complete

Workstream 0.1 Task 7 landed `src/shared/lib/hub-field-aad.ts` and wired `hubFieldAad(recordId, fieldName)` through `encryptHubField` / `decryptHubField` on the client. The server continues to store the ciphertext opaquely. Transplantation resistance is now locked in by a real cryptographic test in `tests/api/aead-binding.spec.ts` (added by post-impl review), which proves a ciphertext bound to `(recordA, fieldX)` fails to decrypt under `(recordB, fieldX)`, `(recordA, fieldY)`, and `(recordB, fieldY)`. If the `hubFieldAad` formula ever drifts, the test will flip.

- **`drizzle/migrations/0054_tier1_items_key_indirection.sql`** adds `users.items_key_version INTEGER` and `users.items_key_wrapped TEXT` (both NULL until a client materialises its `items_key` via `generateItemsKey(master, 1)`). The contract is documented in the migration header: monotonic integer starting at 1, base64 of the 40-byte AES-KW ciphertext, server treats both columns as opaque. The 40-byte AES-KW wrap is byte-equivalent across classical and PQ master KEKs, so rotating primitives costs O(users) rewraps of a 40-byte blob rather than O(artifacts) re-encryption.
- **`src/shared/items-key.test.ts`** (new, colocated `bun:test`) covers the wrap/unwrap round-trip, version bump, and rewrap-under-new-master byte-equivalence invariants.

**FIX rows explicitly deferred (require coordinated encrypt+decrypt migration across many columns):**

- **Envelope-encrypted fields on `contacts`, `user_signal_contacts`, `conversations`, `call_records`, `bans`** — every `encryptedFoo` + `fooEnvelopes` pair currently encrypts with label-only AAD (`utf8ToBytes(label)`) via `cryptoWorker.envelopeEncryptField(...)`.
